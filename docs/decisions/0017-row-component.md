# 0017 One component per data row (3.11)

Status: Proposed (2026-10-19), for Zahid. No issue or pull request yet. Revised on 2026-10-19 after two independent reviews (see Consultation).

## Context

A live list redraws every row when one of them changes. The Task Monitor of frontendx, the first consumer of ADR 0016 (hundreds to thousands of tasks, `rowKey`, `virtual`, `flash` with `rowsUpdate="live"`, `groupBy`), gets the whole task list again on every SignalR message. The consumer keeps the objects of unchanged tasks by reference and replaces only the task that changed, yet every drawn row is built again, every cell slot runs again and every row is patched. With `virtual` that is the window (tens of rows) on every message; without it, every row.

Vue decides what to redraw per component. The body (`packages/vue/src/parts/table-body.vue`) is one component: it draws every body item (spacer, group row, data row, subtable row) in one flat `<template v-for="item in bodyRows">`, with plain `tr` and `td` elements and the `cell-<field>` slots in the same template. Any reactive change the body reads (a new `rows` array, one selection flag, one flash mark) runs its whole render. Vue then compares the new tree with the old one: elements are cheap to compare, but the vnodes of every row and the output of every cell slot are made again first. The DOM that comes out is the same for the rows that did not change; the work to find that out is spent on every row.

The goal, decided by Zahid: when one task changes and nothing that other rows draw changes with it, only that row is drawn again. "Nothing other rows draw" is meant literally: when the change moves another row's `data-row-index` or `aria-rowindex` (a row added above, a group split, an expansion above with `virtual`), or changes what every row draws (columns, pin offsets), those rows are drawn again, because their DOM changes (K311-8). Success is measured in render counts (`pnpm check:renders`), not milliseconds. The markup stays as it is (C-108); what a cell slot shows can differ from 3.10 in the cases K311-5 lists, decided by the owner.

## Decision

- **Each data row is its own component (K311-1).** A stateful component `TableRow` (`packages/vue/src/parts/table-row.ts`) draws one data row: its `tr`, the utility cells (right panel, expand button, selection checkbox) and the column cells with their `cell-<field>` slots. An unchanged row is skipped by Vue's own props check (`shouldUpdateComponent`): the body still renders, but a row whose props are the same as last time is neither rendered nor patched.
  - The body keeps everything else in its flat `v-for`: spacer rows, group rows, the subtable row, and the loading, empty and load-more rows. Only the `tr v-else` branch becomes `<table-row v-else ...>`, so the structure the comment in `table-body.vue` asks for (no nested `<template>` Fragment, issue #106 family) stays: the subtable `tr` is still a direct sibling in the same flat list.
  - The row vnode is created by the body's compiled template, so it carries the `PROPS` patch flag and its `dynamicProps`, and Vue compares its props. A component vnode made with `h()` inside a block has patch flag 0, and on the optimized path `shouldUpdateComponent` then never compares props: the row would never update again. No directive goes on `<table-row>` either: a vnode with `dirs` always updates.
  - The row's render returns exactly one root, the `tr`, with no sibling comment or text: a Fragment root would bring the #106 problem back, and a template root with a comment is a Fragment in development builds.
  - The row is a render function, not an SFC template. Its cell slots come from a prop (K311-3); a template can draw a slot from a prop only through an extra component per cell, and that component (functional or not) gets a component instance and a render effect of its own (functional components go through `renderComponentRoot` and `shouldUpdateComponent` too), so the slot's reads would track to that cell component instead of the row, one instance per slotted cell would be added, and the render counts could not see it (global mixins and their `updated` hook do not apply to functional components). The render function produces the vnode tree today's compiled `tr` branch produces: the same elements and attributes, the same comment placeholders for branches that are off, the column cells in one keyed Fragment as the `v-for` makes them, and each cell slot through `renderSlot`, the call a compiled `<slot>` makes. The implementation starts from the compiler output of today's branch, using the helpers `vue` exports for compiled code (`openBlock`, `createElementBlock`, `createCommentVNode`, `renderList`, `renderSlot`), so the row's own subtree keeps block optimization. C-108 holds the markup, not the look of the source.
  - Stateful, not functional: both are skipped by the same props check, but a stateful component has the lifecycle hooks the render budget counts (`updated`) and a named instance in Vue DevTools (K311-11).

- **The row gets values, not functions (K311-2).** A row that calls a shared function during its render (`isSelected(row, index)`, `flash.row(row, index)`) reads the shared state behind it (the selection map, the flash version). Then every row depends on that state and redraws on every change of it. So the body computes each row's values in its own render and passes them as props:

  | Prop                                       | Value                                                                                                                       | Changes when                                          |
  | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
  | `row`                                      | the consumer's row object, by reference                                                                                     | the consumer gives a new object for that row          |
  | `rowKey`                                   | `keyOf(row, index)`, the key the body uses for the `v-for`                                                                  | the key of that row                                   |
  | `index`, `aria`, `pinned`                  | `data-row-index`, `aria-rowindex` (virtual only), `data-pinned-row`                                                         | the row moves, or what is above it changes (K311-8)   |
  | `kind`                                     | `rowKind(row, index) \|\| undefined`                                                                                        | the kind of that row                                  |
  | `selected`, `expanded`, `expandable`       | booleans; `expandable` only with `hasSubtable` (C-98)                                                                       | that row's state                                      |
  | `flash`                                    | that row's marks (K311-6), or `undefined`                                                                                   | a flash of that row starts, restarts or ends          |
  | `cells`                                    | one descriptor per drawn column: field, column, `td` attributes (`data-field`, `data-type`, pin, `role`), slot name or none | columns, order, types, pin offsets, slot set, `roles` |
  | `utilities`                                | which utility cells are drawn and their attributes                                                                          | utilities, left pinning, offsets, `roles`             |
  | `labelPanel`, `labelExpand`, `labelSelect` | the three row texts, as strings                                                                                             | those texts                                           |
  | `roles`                                    | `scrollBody` (C-102)                                                                                                        | `scrollBody`                                          |
  | `slots`                                    | the body's slots object (K311-3)                                                                                            | never (one object per body instance)                  |
  | `flashBind`, `pinRow`                      | stable functions                                                                                                            | `flash` turned on or off; never                       |
  - **`cells` and `utilities` are kept by value, not only `computed` (review finding).** `entries` is not stable across a rows-only update: it calls TanStack's column getters, which read `table.options`, and a new `rows` updates TanStack's options store, so the `computed` returns a new array of new entries with the same columns (probed by astra). The body therefore builds `cells` and `utilities` in a `computed` that compares the new descriptors with the last ones (the same column object and index, type, pin side and offset, slot name, `roles`) and returns the previous array when all are equal. The `pinAttrs` objects live inside those kept descriptors, so they are not made per render. An internal spec locks it: after a rows-only update the `cells` and `utilities` props of every row are the same objects. Making `entries` itself stable would also change what the header and the filter cells redraw; that is its own change.
  - **The labels are three strings.** `query-table.vue` makes a new labels object whenever `props.labels` changes identity (`resolveLabels`), so a consumer that writes `:labels="{ ... }"` inline would redraw every row on every render. Strings compare by value.
  - **Row actions are emits.** `TableRow` declares `toggle`, `toggleSelected` and `rightPanel` as emits, and the body listens with `@toggle`, `@toggle-selected`, `@right-panel`. `hasPropsChanged` skips declared emit listeners (`isEmitListener`), so the body's handlers may be new functions on every render without redrawing a row. `pinRow` stays a prop (the slot's `pinRow` calls it with the row's own `row` and `index`); it is the stable `state.rowPinning.pin`.
  - The row never receives the body item itself. The items are new objects on every recompute (`bodyRows` maps `rows` to new `{ row, index, pinned }`; the virtual window builds `{ ...all[q], aria }`), so an item prop would differ every time and no row would ever be skipped.
  - Functions passed to the row are called only from events, from the cell slot's `pinRow` when the consumer calls it, or after the row has rendered (`flashBind`, K311-6). The row's render calls only module functions that read nothing shared (`valueAt`, `String`) and the slot functions (K311-3).
  - A consumer function given inline (`:row-kind="row => ..."`, `groupBy`, `rowExpandable`) is a new function on every render of the consumer. It reaches only the body, which calls it and passes the result; the row sees the same value and is skipped.

- **Slots reach the row as one stable object, never as forwarded slots (K311-3).** The obvious way, `<table-row><template v-for="name in names" #[name]="p"><slot :name="name" v-bind="p" /></template></table-row>`, makes the row update on every render of the body. Checked in the Vue source this repository resolves (3.5.43), and confirmed by astra against `componentSlots.ts` and `componentRenderUtils.ts` of that tag:
  - The compiler marks a component's slots dynamic when a slot name is not static, a slot sits under `v-if` or `v-for`, or the component is inside a `v-for` or another slot's scope (`buildSlots` in `@vue/compiler-core`, `hasDynamicSlots`). Dynamic slots set the vnode's `DYNAMIC_SLOTS` patch flag (1024) and the slot object's flag to `DYNAMIC` (2).
  - `shouldUpdateComponent` (`@vue/runtime-core`) returns `true` for a vnode with `DYNAMIC_SLOTS` before it looks at the props. On the unoptimized path it returns `true` for any slots object without `$stable`.
  - A forwarded slot (`<slot>` inside a child's slot, flag `FORWARDED`, 3) becomes `DYNAMIC` and gets the patch flag whenever the forwarding component's own slots are not `STABLE` (`normalizeChildren`). The body's slots are already dynamic: `query-table.vue` forwards them with `<template v-for="name in bodySlotNames()" #[name]>`, so the body itself is forced to update on every render of `QueryTable`. That is fine for the body, but forwarding once more would force every row.
  - `updateSlots` copies the new slot functions into the same `instance.slots` object (or keeps it untouched for `STABLE`) before the body renders, and deletes the ones that went. The object's identity does not change for the life of the component; the development `useSlots()` proxy is cached too. A `DYNAMIC_SLOTS` flag of an ancestor does not travel through an ordinary prop to a row vnode without children.

  So the body passes its own slots object (`useSlots()`) as the `slots` prop, the same object on every render. The row reads `slots['cell-<field>']` when it renders and calls it with `renderSlot(slots, name, props)`: whenever it renders, it calls the latest function. `cells` keeps slot names, never slot functions. Which cell slots exist is not reactive (slots are not), so `QueryTable` passes the set of body slot names to the body as a string, as it already does for the header (`headerSlotNames`), and the body builds `cells` from it; a slot that comes or goes changes the string and redraws every row. Tests lock the skip and, separately, the freshness (K311-12).

- **A cell slot's reactive reads belong to its row (K311-4).** Today a cell slot runs inside the body's render, so a reactive value it reads becomes a dependency of the whole body: a duration cell that reads a ticking clock redraws every row on every tick. With the row component the slot runs inside its row's render, and a reactive read draws that row again, and no other row and not the body. The design keeps this by calling the slot in the row's own render (K311-3), not in the body's. A reactive value that every row's slot reads still redraws every row: the clock belongs in the cells that show it. The `group` and `subtable` slots stay in the body: what they read redraws the body, which then redraws no unchanged row.

- **A cell slot is called again when its row is drawn again, not when its owner renders (K311-5).** A compatibility exception in a minor release, decided by the owner (P9: a breaking change is decided explicitly before it is made; see Owner decisions).
  - What changes. In 3.10 every render of the body calls every cell slot, and the body renders whenever `QueryTable` renders: on any prop change (a new `rows` array included, for every consumer) and, when the consumer's slots compile dynamic, on every render of the consumer. From 3.11 a cell slot is called again only when its row is drawn again (C-106) or when a value it read reactively during its last call changes (K311-4). The boundary is exactly that: the dependencies read during the previous call of that slot for that row.
  - What a slot can stop showing, until its row redraws:
    - a value that is not reactive: `Date.now()`, a plain variable, a plain (non-reactive) row object mutated in place. Give the row a new object instead.
    - a value captured from an outer scope (`v-for`, an outer `v-slot`): a primitive, and also a reactive object that the outer scope replaces with another one. The unchanged row stays subscribed to the old object; neither the replacement nor later changes of the new object redraw it.
    - which of two definitions of the same slot name is used, when the consumer switches them with `v-if`/`v-else` on the `<template #cell-x>`: the set of slot names does not change, so no row redraws.
    - event handlers and directive bindings in the slot that close over such outer values: they keep acting on the old values.
  - What stays live: slot props (`row`, `cellValue`, ...), reactive state read inside the slot (refs, `computed`s, stores, `inject`ed refs, the reactive locale behind `t()`), and `$attrs` read inside the slot.
  - The migration for a consumer: read the value inside the slot from reactive state (`{{ account.value.name }}`, or a getter), not from a variable the outer template captured; put the condition inside one slot (`<template #cell-x><A v-if="mode === 'a'" /><B v-else /></template>`); call a function that reads the current state at click time instead of binding a captured value; give a changed row a new object.
  - The markup of a given state is unchanged (C-108) and the equivalence gate finds no difference, but that does not mean every displayed value is the same in every sequence of updates: the cases above are the exception.
  - Why not keep the refresh: the only signal is that the slot functions changed, and with dynamic slots they change on every render of the owner, whether or not anything the slot shows changed. The Task Monitor is such a consumer: `TaskMonitorTable.vue` forwards every slot with `<template v-for="(_, name) in $slots" #[name]>`, and renders on every SignalR message because its `rows` prop changed. Redrawing every row when the slot functions change would redraw every row on every message, and the goal would not be met for the consumer it is for. The Task Monitor's cell slots were checked (Fable): they read only their `row`, `t()`, `computed`s and the injected clock, none of the cases above.

- **A row's flash is one value per row (K311-6).** Today the body calls `flash.row(row, index)` and `flash.cell(row, index, field)` per row and cell. Both read the flash `version` (one `shallowRef` for the table) and the clock (`performance.now()`, through `live`). In the row that would make every row depend on `version`, so every flash anywhere would redraw every row.
  - The body asks the flash once per drawn row for that row's marks: `FlashView` gains `of(key): RowFlash | undefined`, where `RowFlash` is `{ row?: FlashPhase; cells?: Readonly<Record<string, FlashPhase>> }`, the `data-flash` value of the row and of each cell with a live mark. It reads `version` and the clock as the body's render does today, so a mark is drawn or not by the same test at the same moment.
  - Equal marks give the same object. The cache key of a row is the set of its live marks after `live(mark, now)`, as copied numbers: for the row and each cell, the field, the phase and the generation (`gen`). It never keeps references to `Mark` objects, which `marks.ts` updates in place on a restart. While that set is the same the previous `RowFlash` is returned, so a row that is still flashing is skipped while another row starts its flash. A restart in the same frame keeps the phase but bumps the generation, so the row redraws and `bind` writes the new `--qt-flash-elapsed`, as it does today. A mark that ends drops out of the live set, so the row redraws and `bind` removes the elapsed time. The cache is pruned with the marks (P8).
  - **`bind` reads nothing reactive (review finding).** Today `bind` reads `o.rows()[index]` to find the row's key. `onVnodeBeforeMount` and `onVnodeUpdated` run while the row's render effect is active (`invokeVNodeHook` does not pause tracking), so in the row that read would subscribe a newly mounted row to the whole `rows` array, and the next replacement would redraw it too (probed by astra: updates `[1, 1]` for one changed row). The row therefore calls `flashBind(el, rowKey)` from its root `tr`'s `onVnodeBeforeMount` and `onVnodeUpdated`, with the key the body passed (`rowKey` prop), and `bind` reads only the non-reactive marks and its `WeakMap`s. Reading the row's own `rowKey` prop there tracks only the row's own props.
  - Today `bind` runs for every drawn row on every body render; after this change it runs for a row only when that row renders. That is the same outcome: `bind` writes only for a row whose live marks changed (which redraws it), whose cells were mounted since (a column shown, which redraws every row), or whose `style` binding Vue dropped (a redraw). A row with no mark and nothing bound returns at its first check today.
  - With `flash` off the body passes `undefined` and calls nothing per row (C-95).

- **The expansion snapshot stays (K311-7).** The body fills `expandedSnapshot` once per render, and both the row's `expanded` prop and the subtable row's `v-if` read it, so the chevron and the detail row cannot disagree within one render. Cell slots now run in the rows' renders, after the body's render has read the snapshot. The snapshot is kept: the `subtable` and `group` slots still run inside the body's render. The existing regression test (`expand.slot-churn.spec.ts`) writes the rows from `@vue:mounted`, not while a slot is evaluated; a new test writes reactive state once, synchronously, inside a `cell-<field>` slot's evaluation and checks both the chevron and that the subtable `tr` is in the DOM.

- **The virtual body and its measurement do not change; what moves a row redraws it (K311-8).** The window finds rows in the DOM: `:scope > tr[data-row-index]`, `tbody.children`, `qt-group-row` and `qt-subtable-row` neighbours, one `ResizeObserver` on the drawn `tr` elements. The row component's `tr` is a direct child of the `tbody`, as before. A row that moves inside the window keeps its instance (keyed by `rowKey`, as the `tr` is today).
  - A row's `data-row-index` and `aria-rowindex` follow what is above it. A row added or removed above, a replaced row whose new group key splits or merges a group run, and, with `virtual`, an expansion above (the subtable row counts in `aria-rowindex`) all change the indexes of the rows below, which then redraw: their DOM changes. In a list where new rows come in at the top, every drawn row redraws on each new row; with `virtual` that is the window. These are kept, not worked around (C-40).
  - A row whose own slot changes its height redraws only itself; the `ResizeObserver` sees the new height and the window may move, which renders the body. A test covers it: with `virtual`, a reactive value read by one row's slot makes that row taller without any other change, and the spacer heights follow.

- **No listener per row (K311-9, P8, C-28).** `contextmenu` stays on the `tbody` (`useCellView`), and `focusin` and `focusout` (C-86) stay on the body's root. The row adds no listener of its own. The handlers that already exist on its controls (the right panel button, the expand button, the selection checkbox) are unchanged. The row sets `inheritAttrs: false`, so nothing given to it by mistake falls through onto the `tr`.

- **There is no option; the cost is one instance per drawn row (K311-10).** The row component is always used: a second code path would double the DOM tests, and the off path of an option would be the slow one. What it costs: one component instance, one render effect and one props object per drawn row. With `virtual` that is the window; without it, every row on the page. Mounting a large table creates those instances, so the `mount` scenario's timing is reported before and after in the pull request (1000 rows; the `filter`, `sort` and `page` timings too), next to the counts. The component fixture of `pnpm check:size` grows; the budget is raised in the same change with a one-line reason (P8).

- **`TableRow` is internal (K311-11).** Its name shows in Vue DevTools and in the render counts (`name: 'TableRow'`, next to `table-body`), so a consumer can see which rows redrew. It is not exported, not part of `contract/api.json`, the DOM contract or `CONTRACT.md`, and may change in any release. The README names it only where it explains how to read the DevTools tree.

- **Tests lock the skip and the freshness (K311-12).**
  - Skip: a browser contract test mounts a 200-row table with `rowKey` and counts how often each row's cell slot is called; it replaces one row object and expects one call for that row and none for the others. It repeats this with `virtual`, `flash`, `groupBy`, `scrollBody`, and with the slots forwarded by a wrapper with `<template v-for="(_, name) in $slots" #[name]>` (the Task Monitor's pattern); and with that wrapper, `virtual` and `flash` together after scrolling, so the replaced row is one mounted after the flash started (the case of the `bind` finding). It also asserts the replaced row's new content and that the other rows' elements are the same nodes.
  - Freshness: through the forwarding wrapper, the test gives a same-name slot a new closure, checks that an unchanged row is not called, then redraws that row by another input (its selection) and checks that the new closure is the one called.
  - Structure: an internal spec asserts that every row vnode the body creates has no children, no `DYNAMIC_SLOTS` flag, no `dirs`, and a `PROPS` or `FULL_PROPS` patch flag (`patchFlag & (8 | 16)`), and that the row's subtree root is one `tr` element vnode; and that `cells` and `utilities` keep their identity across a rows-only update.

## Options considered

- **`v-memo` on the row's `tr` in the body template.** Rejected. `v-memo` skips the whole subtree unless one of its listed values changed, reactive reads inside it included: a cell slot reading a ticking clock would stay stale until the row's own values change. It also keeps every slot's reads in the body (K311-4), so a clock still runs the body's render for every row.
- **The row as an SFC template, each cell slot drawn by a small functional `CellSlot` component (Fable's preference).** Rejected: see K311-1. It reads well and keeps block optimization, but adds an instance per slotted cell, moves the slot's tracking from the row to that cell instance, and hides those updates from the render budget. The render function keeps the block optimization by using the compiler's helpers.
- **One component per cell.** Out of scope. A row is the unit that changes in a live list (a task replaced as a whole) and the unit `flash.bind` and the virtual measure work on. Per-cell components multiply the instances by the column count.
- **Redraw every row when the slot functions change (the strict form of K311-5).** Rejected for the reason in K311-5: with dynamic slots, which the Task Monitor has, it redraws every row on every message.
- **Forward the slots to the row (`<template #[name]>`).** Rejected (K311-3): it forces every row to update on every render of the body.
- **Make `entries` stable in `useQueryTable` instead of keeping `cells` by value in the body.** Not now: it would change the header's and the filter cells' redraws and their render counts, which is a change of its own.

## Scope

In: the data row of the body, in both bodies (`scrollBody` on and off); the props, slots and flash changes K311-1 to K311-12 need; the render scenarios, the tests, the docs and the playground page below.

Out, each its own change:

- Per-cell components; the header, filter cells and footer rows (they re-render with the rows today for reasons of their own: in the `live` scenario the header and the four filter cells re-render once per change); a stable `entries`.
- `v-memo`, and any new prop or option to switch the row component off.
- Dropping or changing `data-row-index`, so an insertion above a row would not redraw it (DOM contract, C-40).
- The `group` and `subtable` slots in components of their own.
- Changes to frontendx (the Task Monitor keeps unchanged rows by reference already; a check of that is in the pull request, not in this repository).

## Rules (drafts)

- **C-106 A row is drawn again only for its own inputs.** A data row is drawn again only when its row object (by reference) or its key, its index in `rows`, its `aria-rowindex`, its pinned position, its `rowKind`, whether it is selected, expanded or can expand, or its live flash marks change, or when an input every row draws changes: the drawn columns (order, type, pinning and its offsets), which `cell-<field>` slots exist, the utility columns, the three row labels, `scrollBody`, and `flash` turned on or off. Its index and `aria-rowindex` change when a row is added or removed above it, when a group run above it splits or merges, and with `virtual` when a row above it expands or collapses; it is then drawn again. A new `rows` array that holds the same row objects in the same order draws no row again and mounts none. A `cell-<field>` slot of a row that is not drawn again is not called. Group rows, spacers and the subtable row are drawn by the body, as in 3.10. Source: own. Tested by counting cell slot calls per row (K311-12) and by the render budget.
- **C-107 A cell slot is called again with its row only.** A `cell-<field>` slot runs in the render of its row: a reactive value it read during its last call draws that row again, and no other row and not the body. A cell slot is called again only then or when its row is drawn again (C-106); a render of the component that gives the slot does not call it. So a value the slot shows that is neither in its slot props nor read reactively inside the slot (a non-reactive value, a value or object captured from an outer `v-for` or `v-slot` scope, a choice between two same-name slot definitions made outside the slot) is not refreshed until the row is drawn again, and handlers in the slot keep the values they captured. The `group` and `subtable` slots run in the body's render. Source: own.
- **C-108 Row component and DOM contract of 3.11.** The body's markup is the one of 3.10 for every state and every transition the tests draw: the same elements, attributes, text and comment placeholders. The table adds no listener per row; `contextmenu`, `focusin` and `focusout` stay on the `tbody` (C-28, C-86). Source: own. Tested by C-40 and C-95 unchanged, the equivalence gate, and a markup snapshot of `tbody.innerHTML` taken from 3.10.0 (see Checks).

## API

None. `TableProps`, `TableSlots`, `CellSlotProps`, `useQueryTable` and the exposed methods are unchanged; `contract/api.json` and the API reports do not move; the DOM contract (`contract/dom.ts`) gains no entry. The behavior change of C-107 is recorded as a compatibility exception (K311-5) in the release notes.

Internal only: `TableRow`, its props and emits, the `slotNames` prop of the body, `FlashView.of`, the new `bind(el, key)` signature and the `RowFlash` type in `flash/use-change-flash.ts`. `FlashView.row` and `FlashView.cell` go once nothing calls them.

## Checks

- **Render budget.** `scripts/render-budget.json` gains, per scenario, `rowUpdates` and `rowMounts`: the exact number of `TableRow` updates and mounts, asserted like `queryUpdates` (counts are deterministic). `TableRow` is left out of `libraryUpdates`, so `maxLibraryUpdates` keeps meaning what it meant in 3.10 (the body, the header, the root and the filter cells) and the existing scenarios keep their limits. `scripts/measure-renders.mjs --check` validates the two new fields; without that the budget would not check them. `MeasureHost.vue` is extended with a button that replaces one row object and keeps the others, one that gives a new array of the same objects, `v-model:selection`, an expansion toggle, a `clock` ref, a state of the host that the table does not read, a wrapper that forwards its slots with `<template v-for="(_, name) in $slots" #[name]>`, and a fixed-height scroll box for `virtual`. The flash scenarios keep `--qt-flash-duration: 60s`, so no flash ends while they count. New scenarios:

## Consequences

- When one row object is replaced and nothing above it moves, one row component renders. The body still renders once (it builds one vnode per drawn row and compares its props); with `virtual` that is the window.
- A cell slot's reactive reads cost its row only. A clock read in a few cells redraws those rows, not the table.
- A row whose props are equal is not patched, so its DOM, the state of components in its cell slots and its flash binding are untouched.
- A cell slot is no longer called again because its owner or `QueryTable` rendered (K311-5, C-107). Values it read reactively stay live; captured, non-reactive and outer-scope values do not.
- Row-wide changes still redraw every row: a new `rows` array of new objects, a column change, a slot that comes or goes, a row added above, a group split above, an expansion above with `virtual`. The budget's numbers show where.
- Mounting creates one component instance per drawn row; reported, not budgeted.
- The body's render and the row's render are two places to keep in step: a new per-row state is a new row prop computed in the body (a value, kept by value when it is an object), never a function the row calls during its render.

## Trade-off

The table has one more component and a list of row props that must stay values, kept by value where they are objects, and a cell slot is no longer called again just because its owner rendered. In exchange a live list costs one row per changed row, a cell that reads a clock costs its row, and the render budget can say how many rows were drawn again.

## Owner decisions

Decided on 2026-10-19 under the autonomy Zahid gave for this change (success measure: one changed task, one redrawn row).

- K311-5 is accepted: a cell slot is called again only with its row, or when a reactive value it read changes. Keeping the 3.10 refresh for dynamic slots would miss the goal for the consumer it is for (`TaskMonitorTable.vue` forwards its slots with a `v-for`).
- Rows inserted above others redraw the rows below them (`data-row-index` moves); this stays out of scope. The goal is about a changed row, not an added one.
